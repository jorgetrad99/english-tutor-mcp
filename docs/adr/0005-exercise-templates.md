# 0005 — Exercises and lesson displays as learner-approved templates

- **Status:** proposed
- **Date:** 2026-11-02
- **Deciders:** Jorge
- **Spec:** `docs/superpowers/specs/2026-11-02-subjects-and-notes-design.md` section 15 (amendment)
- **Amends:** `docs/adr/0004-subjects-context-beside-english.md` decisions 6 and 8
- **Plan:** `docs/superpowers/plans/2026-11-02-subjects-slice-a-notes-and-search.md` Task 4b

## Context

Slice A, as built through Task 4, stores per note one free HTML document per artifact (`save_artifact`, capped at 40,000 bytes after commit `fb42da8`), plus exercises and quiz items as fixed structured rows. Slice B was going to grade fixed item kinds (`note_id`, `interval_id`, `quiz`, `exercise`), and the practice app was going to carry one renderer per kind.

Looking at a real guitar course showed two problems. Claude would write a new HTML page for every drill, so the same exercise type (multiple choice, "find these notes on the piano", "which note did you hear") would exist many times, each slightly different, untestable and impossible to grade on the server. And a free page can hold its answer in its own code, which breaks the rule that the server grades.

On 2026-11-02 the author decided, in four steps:

1. An exercise type is a reusable template. A note stores "template plus parameters". Claude lists the subject's templates, fills the matching one, and proposes a new template only when none fits, creating it after the learner says yes.
2. There is no free per-note HTML. Lesson displays such as tablature and chord diagrams are templates too. Every instance is stored with its parameters and answer key, so it can be reused and graded later.
3. The server ships no built-in templates. Claude writes every template, guided by recommendations the server serves.
4. The design must work for any subject (languages, math, history, programming, cooking, music), not only music. The first draft of this ADR carried music into the server contract (`pitch`, `pitch_list` and `interval` parameter types, `ear_note` and `ear_interval` generators, octave-free pitch grading, frequencies computed by the server). The server must be domain-neutral and give Claude what it needs to work out what fits each subject.

## Decision

1. **Templates by exercise type, all per subject.** A template is HTML, a closed parameter schema (names, roles `prompt`, `answer_key`, `reveal`, `pool`, caps) and a grading kind from a closed enum, with purpose `exercise` or `display`. Templates are immutable; a replacement is a new row; templates are replaced or retired, never deleted. Claude creates each one with `save_template` after the learner agrees (`learner_confirmed: true` in every call, plus response rules); on a subject's first ingest one yes covers a starter list shown in full in one message.
2. **A domain-neutral contract.** Parameter types are generic only: `text`, `text_list`, `text_table`, `integer`, `integer_list`, `number`, `number_list`, `boolean`, `pool`. Grading kinds are generic only: `none`, `choice_index`, `exact_text`, `exact_set` (partial credit by overlap), `exact_sequence` (ordering, scored by longest common subsequence), `numeric` (with an absolute tolerance), `self_report`. Text answers are normalised by a closed rule (NFKC, trim, inner whitespace, case fold, accent fold, surrounding punctuation), and a template may choose `keep_accents` (languages) or `exact_case` (code, formulas). The server has no pitches, intervals, frequencies, octaves or ear banks; a field-specific behaviour such as playing a tone or drawing a keyboard lives in a Claude-written template and works from its parameters. A template flag `needs_view` marks items that cannot be done from text, so text mode skips them without the server knowing why. The subject's `exercise_kinds` value `ear` becomes the generic `drill`, and the practice kind of a template is derived by the server, not sent by Claude.
3. **Varied items from pools.** A template may draw from a `pool` parameter (2–200 entries `{cue, answer, accept?, explain?, order?}`) by a closed rule: `one` (flashcard), `one_of_choices` (the drawn answer among distinct distractor answers) or `ordered` (put drawn entries in order). The server draws with a seeded generator of its own, stores the seed and the picked indexes on the showing, derives the answer key from the stored draw and grades it. Authored instances (one instance per item, least recently shown first) stay the path for unique items; pools are recommended for repetitive recall and recognition. Ear training is one example: a pool of note names in a Claude-written template that plays them.
4. **No built-ins; a served, versioned, subject-agnostic template guide.** The guide teaches the decision path (analyse the subject's goal and material; choose among recall, recognition, production, application, sequencing, self-reported practice and display; map each to a grading kind; authored or pool; propose a starter set of 2–4 templates; reuse before proposing; take parameters from the note) and the contract (structure, the JSON parameter tag, types, roles, grading kinds and answer shapes, pools, how answers are sent, the size cap, sandbox limits), display templates (tables, timelines, diagrams, code, tablature), accessibility and themes, and worked examples from four fields: a language vocabulary flashcard, a math numeric answer, a history timeline ordering and a music ear item from a pool. It is delivered by a read tool, `get_template_guide(section)`, and its decision path and contract sections are returned inside `list_templates` when the subject has no template yet. The subjects paragraph of the server instructions and the descriptions of `get_subjects`, `save_notes`, `list_templates` and `save_template` carry the path without any subject assumption. An MCP prompt (user-invoked), an MCP resource (uneven model access across clients), an installed Claude Skill (per-user install, drifts from the server) and tool descriptions (120-word cap) were considered and rejected as the primary channel. The contract tables and the grading-kind map in the guide are generated from the domain constants. `TEMPLATE_GUIDE_VERSION` is pinned to a hash of those constants by a test, and `save_template` rejects a stale `guide_version`.
5. **No free HTML.** `save_artifact`, `get_artifact` and `note_artifacts` are removed before release. A case that fits no template becomes a new template.
6. **Every instance is stored.** An instance (template, full parameters with the answer key, `prompt_text`) is an immutable row, deduplicated by a content key and reusable across sessions. A practice item is one showing of an instance; `record_result` grades the showing against the stored instance and its stored draw.
7. **The server grades and never runs template code; correctness never depends on the template.** The server validates parameters against the schema and strips answer-key, reveal and pool parameters before anything reaches a client. Parameters reach the HTML only as JSON inside `<script type="application/json" id="tutor-params">`, with `<`, `>`, `&`, U+2028 and U+2029 escaped. The server makes two insertions at a fixed marker (the payload and a server-owned bridge script) and never substitutes values into markup.
8. **Same HTML guard and sandbox as before.** Template HTML passes `check_html` plus the marker rule, is capped at 40,000 bytes, and is shown only in sandboxes: the website frame with `sandbox allow-scripts` and no network, a chat artifact, or a nested opaque frame inside the MCP App.
9. **Rendering is honest about MCP Apps.** `ui://` resources are static, so the practice app is a shell that receives each composed document in the tool result. The app shows a template only in a nested `srcdoc` sandboxed frame (new spike 05 item 8) and relays one message type as `record_result`. It never replaces its own document with a template, because LLM-written code there could call any tool. If item 8 fails, the app draws a plain view from the grading kind and `needs_view` items wait. Chat artifacts and a text rendering, which every result carries, cover the other clients.
10. **Rewrite migration 0006 before merge** (slice A ruling 7) instead of adding a 0007. `note_artifacts`, `exercises` and `quiz_items` become `exercise_templates` and `template_instances`, with forced RLS, `_own_rows`, composite `(col, user_id)` foreign keys and narrow grants (no `UPDATE` on instances, no `DELETE` on either). Nothing before 0006 changes. Practice stays `0007`, topics `0008`.
11. **Unreleased tools change in place.** `save_subject`, `get_subjects`, `save_notes` and `get_note` change shape and the two artifact tools disappear, because none of them has been merged or deployed. The "new tool for a breaking change" rule binds from the merge to `main`.

## Consequences

- One HTML file per exercise type and subject: approved once, reused by every note, graded on the server. Claude's ingest output shrinks to parameters.
- Any subject works with the same server code: a new field needs new templates, written by Claude with the learner's yes, never a server change. The price is that field-specific comfort the first draft gave for free (enharmonic and octave-free note grading, server-computed frequencies) moves into content: accepted spellings go into `accept`, frequencies are computed by the template's own script.
- The first ingest of each subject starts with template proposals and one or more learner confirmations before any note carries an exercise. Quality varies with what Claude writes; the guide's worked examples and the validator bound it, and grading does not depend on it.
- The MCP surface for subjects goes from eleven to fifteen tools (`get_template_guide`, `list_templates`, `save_template`, `create_instance`, `get_instance_view`, `show_exercise` added; `save_artifact`, `get_artifact` removed). Twenty-four tools in all.
- Already-built slice A code is reworked: the domain (`notes.py`, `html_guard.py`, a new `templates.py`), the guide files, ports, memory, Postgres repos, `tables.py`, migration 0006, MCP schemas, rules and instructions, and their tests. Slice B changes before it starts: items reference instances and store their draw, grading comes from `tutor.domain.templates`, `show_exercise` and the `class` session mode are added (a class session counts toward attendance when at least one item is answered), the ear banks disappear, and drill items are showings of pool instances.
- A pool's drawn cue is sent to the client. When the cue identifies the answer (a note name the template plays as a tone), a learner who reads the code can find it; this is accepted for one's own practice, and the server neither knows nor checks what a cue means.
- Bridge texts follow the learner's interface language (Spanish only in v0); the guide is in English, because its reader is Claude.
- Inside the MCP App, the nested-frame path is unverified until spike 05 item 8 runs. Until then, templates in chat are shown as artifacts or text, and the app's plain view is the fallback.
- LLM-written template HTML can carry a prompt injection from course text. The boundary is the sandbox, the no-network policy, and keeping templates away from the app's host channel; the validator is hygiene.
- A change to the grading contract now means a guide version bump; templates saved under an older guide stay valid (they were validated then, and grading reads only the stored instance).
